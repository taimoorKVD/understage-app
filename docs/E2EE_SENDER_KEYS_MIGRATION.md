# Understage E2EE: libsignal sender-keys migration

**Status:** design document only. No code has been changed.  
**Date:** 5 November 2026  
**Decision that triggered this document:** encrypted group chats should move to official libsignal sender keys so a 200-person Company workspace can be end-to-end encrypted, matching the demonstration video. This note records the security properties, data-migration impact, native-build impact, licensing constraints, and the honest UI claims that may be made after each phase.

This is a plan for review. Implementation must not start until the licensing go/no-go in §6 is decided in writing.

---

## 1. Purpose and scope

The current Understage client encrypts every message separately for every member with TweetNaCl `nacl.box` (X25519 + XSalsa20-Poly1305). That fan-out is honest and works, but it does not scale to the video’s 200-person Hamlet workspace: ciphertext size and CPU grow linearly with membership, the server stores one row per recipient, and the product already refuses to send when `memberCount` exceeds the 50 members returned by `serializeConv`.

Sender keys change the cost model. After a one-time distribution of each sender’s group key over pairwise Signal sessions, each subsequent group message is a single ciphertext. That is how Signal and WhatsApp encrypt large groups. It is the smallest protocol change that can make the video’s “200-person workspace chats are E2EE” claim true without pretending the current 50-member fan-out is something it is not.

Out of scope for this document:

- Any visual redesign, theme, typography, or navigation change.
- Multi-device accounts, Secure Value Recovery, or desktop linking.
- Making announcements end-to-end encrypted (they stay server-readable so acknowledgement tracking and quiet-hours holding can work; the compose screen already says so).
- CallKit, VoIP push, or TURN (those are separate calling infrastructure items).
- Purchasing Signal, OpenE2EE, or any other commercial license.

## 2. Current implementation (as built)

Sources: `shared/e2ee.ts`, `src/lib/crypto.ts`, `src/lib/engine.ts`, `src/lib/secure.ts`, `src/lib/calls.ts`, `server/src/app.ts`, `server/src/db.ts`, `ASSUMPTIONS.md`, `FEATURE_MATRIX.md`.

### 2.1 Cryptography

| Piece | What it is today |
|---|---|
| Library | TweetNaCl (`tweetnacl` + `tweetnacl-util`), audited port of NaCl. Shared by the app and the server test suite. |
| Identity | One static X25519 key pair per user, generated by `nacl.box.keyPair()`. |
| Private key storage | iOS Keychain via `expo-secure-store`, accessibility `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`. Not the Secure Enclave. The secret is stored as JSON next to the public key. |
| Published material | `PUT /me/keys` accepts a single base64 X25519 public key (`identity_key` on `users`). No device id, no registration id, no prekeys. |
| 1:1 and group messages | `encryptForRecipients` builds one `nacl.box` per member, including the sender’s own copy. The server requires a payload for every member (`MISSING_RECIPIENTS`) and stores them in `message_payloads (message_id, recipient_id, nonce, ciphertext)`. |
| Attachments | `nacl.secretbox` with a fresh 32-byte key and nonce. The key travels inside the boxed plaintext as `AttachmentRef { id, key, nonce, mime, name, size }`. The server stores an opaque blob. |
| Call signalling | SDP and ICE are sealed with `nacl.box` between the two identity keys (`src/lib/calls.ts`). Media is WebRTC DTLS-SRTP. |
| Safety numbers | A custom 60-digit value from iterated `nacl.hash` over `understage-safety-v1:` + user id + public key. It is not a Signal fingerprint. |
| Randomness | `expo-crypto.getRandomBytes` (SecRandomCopyBytes on iOS), injected into TweetNaCl via `setRandomSource`. |
| Devices | Single device. A new phone generates a new identity. Contacts see a safety-number change. There is no ratchet state to migrate. |

`shared/e2ee.ts` already documents the honest scope: this is static-key sealed-per-recipient encryption. It is not the Signal protocol. There is no Double Ratchet, no forward secrecy, no post-compromise security, and no prekey bundles.

### 2.2 The 50-member cap

Three separate limits produce the cap:

1. `serializeConv` loads conversation members with `LIMIT 50`, while `memberCount` is the real `COUNT(*)`.
2. `sendItem` in `engine.ts` refuses to send when `conv.memberCount > conv.members.length`, with the message “Encrypted chat is limited to 50 members in this build”.
3. The new-group screen hard-caps selection at 50 and toasts the same limit.

The create-group API itself allows up to 500 `memberIds`. The 50-member rule is a cryptographic fan-out limit, not a workspace seat limit. Workspace seat limits are separately 50 (Production, £49) and 200 (Company, £149). A Company workspace can already have 200 members; they simply cannot share one encrypted group conversation under the current scheme.

At 200 members, every text message would create 200 `nacl.box` operations and 200 `message_payloads` rows. Voice notes and attachments add a `secretbox` of the file plus those 200 boxes of the content key. That is why the product stops at 50 rather than silently degrading.

### 2.3 What the video claims, and what the UI currently says

The demonstration video presents 200-person Hamlet workspace chats as end-to-end encrypted, and describes setup in Signal-like language: identity key, one-time pre-keys, and Secure Enclave. It also shows encrypted files and encrypted calls.

The shipping UI is more careful than the video, and that honesty must be preserved until the matching protocol exists:

- Onboarding step 5 (`src/app/(onb)/keys.tsx`): “Creating identity key on this phone”, “Publishing your public key”, “Saving secret key to iOS Keychain”. It does **not** mention pre-keys or the Secure Enclave.
- Privacy (`src/app/(app)/privacy.tsx`): “X25519 + XSalsa20-Poly1305, via TweetNaCl”. Announcements are described as readable on the server.
- Chat composer: “Messages and calls are end-to-end encrypted” and “encrypted chats support up to 50”.
- Announcement composer: “Announcements are not end-to-end encrypted”.

The migration is what would let later copy move closer to the video. It must not invent Secure Enclave, pre-keys, or 200-person encrypted groups until those things are real and tested.

## 3. Options compared

Four maintained approaches can encrypt a 200-person group. Custom “sender keys” built on top of TweetNaCl are not one of them.

### 3.1 Official libsignal (Signal Protocol + sender keys)

`signalapp/libsignal` is the library used by Signal iOS, Android, and Desktop. The cryptographic core is Rust. The supported products of the repository are the Java, Swift, and TypeScript wrappers. Use outside Signal is explicitly unsupported; APIs may change without notice.

**Group API (current wrappers, mirrored across Swift / Java / TypeScript):**

- Implement `SenderKeyStore` (`saveSenderKey` / `getSenderKey` keyed by sender `ProtocolAddress` + `distributionId`).
- `SenderKeyDistributionMessage.create(sender, distributionId, store)` produces the SKDM.
- Recipients call `processSenderKeyDistributionMessage(sender, message, store)`.
- `groupEncrypt(sender, distributionId, store, plaintext)` / `groupDecrypt(sender, store, ciphertext)` produce and consume `SenderKeyMessage` (`CiphertextMessageType.SenderKey = 7`).

**1:1 API:** `PreKeyBundle` (identity + signed prekey + one-time prekey + Kyber/ML-KEM prekey), `processPreKeyBundle`, `signalEncrypt`, `signalDecrypt`, `signalDecryptPreKey`. Modern libsignal session establishment is PQXDH (X25519 + ML-KEM), not classical X3DH alone. Safety numbers can use libsignal `Fingerprint` rather than the custom TweetNaCl hash.

**React Native integration reality (2026):**

- `@signalapp/libsignal-client` is a Node native add-on (N-API). It ships prebuilds for Windows, macOS, and Debian Linux. It does **not** run on iOS, Android, or Hermes. It cannot be the app’s runtime.
- `signalapp/libsignal-protocol-javascript` is archived (last push 2021) and must not be used.
- `@privacyresearch/libsignal-protocol-typescript` is unmaintained (last publish May 2023), has no group or post-quantum support, is GPL-3.0-only, and has an open inbound trust-check bug (`isTrustedIdentity()` not awaited).
- Community wrappers such as `p-num/react-native-libsignal-client` show the intended shape (Swift/Java bindings + Expo config plugin) but are not a production foundation.
- The viable path is a first-party Expo native module that talks to the official Swift `LibSignalClient` on iOS (and later the official Java bindings on Android). Protocol-compatibility tests can use the Node package on the Mac, because that add-on does run on macOS.

**Licensing:** GNU AGPL-3.0. See §6. This is the binding constraint.

**Maturity:** Highest of the four options for 1:1 and sender-key groups. This is the protocol the video is describing.

**Build impact on this Mac:** High. See §11.

### 3.2 MLS via OpenMLS (and mls-rs)

MLS (RFC 9420) was designed for groups. Membership changes cost O(log n) rather than O(n²), and post-compromise security is recovered by commits rather than by hoping each sender rotates. OpenMLS is a feature-complete Rust implementation, MIT-licensed, maintained by Phoenix R&D and Cryspen. An independent SRLabs audit (reported 27 May 2026) found eight issues, one High; fixes for seven shipped in OpenMLS 8.1 / 7.3. iOS (`aarch64-apple-ios`) and `x86_64-apple-darwin` are built on CI but not tested there. `mls-rs` (AWS Labs) is dual-licensed Apache-2.0 OR MIT; it has not had a full third-party audit as of the public docs reviewed for this note.

There is no official React Native binding. Published 2026 work (Margelo’s Nitro/JSI series; UniFFI apps such as SkyChat) shows that the entire MLS state machine should live in Rust, with JavaScript holding only opaque snapshots. That is a larger architectural step than wrapping libsignal’s sender-key functions.

MLS does not give Understage Signal-shaped 1:1 sessions, prekey bundles, or Signal safety numbers “for free”. Those would still need a separate pairwise protocol, or MLS used even for two-member groups.

**Licensing:** MIT (OpenMLS) or Apache-2.0/MIT (mls-rs). Compatible with a closed app.

**Verdict:** Better group scaling and stronger PCS than sender keys. Worse fit for the video’s Signal-specific language, and more implementation work on this Expo/iOS stack.

### 3.3 vodozemac / Megolm (Matrix)

`matrix-org/vodozemac` is the maintained Rust implementation of Olm (pairwise ratchet, conceptually close to the Double Ratchet) and Megolm (a sender-key group ratchet). License: Apache-2.0. It is what Matrix clients use for E2EE.

The security trade-offs of Megolm are essentially the same as Signal sender keys: a hash ratchet gives forward secrecy for already-sent messages if old chain keys are deleted; post-compromise security is weak until the sender shares a new inbound session. Matrix documents this explicitly.

A React Native wrapper, `@kinsh/vodozemac-rn` (UniFFI Swift/Kotlin, 0.2.2), exposes `GroupSession` / `InboundGroupSession`. It is early and not battle-tested at Understage’s scale. The native/Rust build problem remains, but the license does not force the app open.

**Verdict:** The closest *architecture* to “Signal sender keys” that can be used in a closed-source app without an AGPL conversation. Weaker brand match to the video (“Signal protocol”) and a less mature RN wrapper.

### 3.4 TypeScript Signal Protocol SDK (OpenE2EE)

`@open-e2ee/signal-protocol-sdk` implements the Signal Protocol in TypeScript on `@noble/curves` / `@noble/post-quantum`, including sender keys and an Expo store adapter. It avoids a Rust/Swift module, which would spare this project another Xcode 26.3 / Swift 6.2 fight. Defaults are post-quantum required (PQXDH + PQ ratchet).

It is dual-licensed: AGPL-3.0-or-later, or a commercial license (publicly listed in 2026 at Startup $5,000/year, Growth $20,000/year, Enterprise/OEM from $50,000/year). Evaluation under AGPL is permitted; shipping a closed app requires the commercial license. Pure-JS crypto on Hermes is slower than a native module, which matters more for a 200-person rekey than for a single 1:1 message.

This option is recorded because it is the lowest *native-build* risk. It is not the recommended library: it is not official libsignal, it is either AGPL or a paid service, and the user asked for a libsignal sender-keys plan.

### 3.5 Comparison

| | Official libsignal | OpenMLS | vodozemac / Megolm | OpenE2EE TS SDK |
|---|---|---|---|---|
| Protocol | Signal (PQXDH + Double Ratchet + sender keys) | MLS RFC 9420 | Olm + Megolm | Signal (PQXDH + DR + sender keys) |

| Membership remove | O(n²) eager rekey (or O(n) per sender, lazy) | O(log n) commit | Same class as sender keys | Same class as sender keys |

## 4. Recommendation

**Recommended protocol:** the Signal Protocol.

- 1:1 (and the channel that distributes group keys): PQXDH session setup + Double Ratchet.
- Groups, including Company workspace chats up to 200 members: Sender Keys.
- Attachments: a random content key inside the Signal or sender-key plaintext, file body encrypted separately (AES-256-GCM, or keep `nacl.secretbox` during the dual-stack period).
- Call signalling: move from static `nacl.box` onto the 1:1 Double Ratchet session. Call media stays WebRTC DTLS-SRTP.

**Recommended library, contingent on §6:** official `signalapp/libsignal`, reached from the app through a first-party Expo native module over the official Swift bindings (iOS first). Do not use the archived JavaScript library, the unmaintained TypeScript port, or the Node N-API package inside React Native.

**Why this, and not MLS or Megolm, as the plan of record:**

1. The user asked for a libsignal sender-keys migration plan, not a protocol replacement.
2. The video’s setup language (identity key, one-time pre-keys, safety numbers, encrypted 1:1 and groups) is the Signal Protocol. Sender keys are how that protocol reaches 200 members.
3. WhatsApp and Signal already run sender-key groups at this size. The O(n²) rekey on member removal is a known, acceptable cost if it is eager, parallel, and visible as “Updating group encryption…”, not a per-message cost.
4. MLS is the better *group* protocol on paper (log-time membership, stronger PCS) and the better license. It is the fallback if libsignal cannot be used legally, or a later evolution, not the first implementation — it would replace both the 1:1 story and the group story and would not let the UI say “Signal-style pre-keys” without also building that pairwise layer.

**If §6 fails (closed app, no App Store additional permission, no Signal commercial license):** do not ship unofficial “we used libsignal anyway”. The fallback with the same *shape* (pairwise ratchet + sender-key group ratchet) and a closed-source-compatible license is vodozemac (Olm + Megolm). The fallback with better group PCS and a permissive license is OpenMLS. Either fallback still needs a native module and a rebuild. Neither should be described in the UI as “the Signal protocol”.

Do not invent a custom sender-key ratchet on TweetNaCl.

## 5. Security properties that change

### 5.1 Today (static `nacl.box`)

- Confidentiality and authenticity between the sender’s static identity key and each recipient’s static identity key.
- **No forward secrecy.** Theft of a user’s identity secret decrypts every past boxed message still stored for that user, and every future one until the key is replaced.
- **No post-compromise security.** Replacing the identity key (new phone) stops the leak only for messages encrypted to the new key. There is no ratchet healing.
- **No prekeys.** Offline session setup is “fetch the published identity key and box to it”.
- **Single device.** A second phone is a new identity. History does not follow. Contacts see a safety-number change.
- The server sees metadata (who talks to whom, when, group membership, ciphertext sizes) and cannot read message bodies or attachment keys.

### 5.2 After 1:1 PQXDH + Double Ratchet

- Session setup uses a prekey bundle (identity key, signed prekey, one-time prekey, Kyber/ML-KEM prekey). A one-time prekey is consumed atomically so two senders cannot be given the same key.
- Each 1:1 message advances the Double Ratchet. Compromising the identity key later does not decrypt prior messages whose ratchet keys were deleted (**forward secrecy**).
- After compromise, further DH/KEM ratchets restore confidentiality for new messages (**post-compromise security**) once both sides send again.
- Safety numbers should switch to libsignal `Fingerprint` over the identity keys (and stay a QR + digit groups UX). An identity change still invalidates verification, as today.

### 5.3 After sender keys (groups)

Sender keys are a deliberate weakening of the pairwise model in exchange for scale.

- Each member who sends has their own sender key: a chain key plus a signature key, named by `(groupId, sender address, distributionId)`.
- The SKDM that carries that key to everyone else is itself encrypted on the pairwise Double Ratchet sessions from §5.2. The server still never sees group plaintext or the sender key.
- Subsequent group messages are one `SenderKeyMessage` for the whole group: AES-encrypted payload, signed by the sender’s group signing key, with a hash ratchet advancing the chain key per message.
- **Forward secrecy (limited):** if the sender deletes prior chain keys, theft of the current sender key does not decrypt earlier messages from that sender. This is weaker operationally than the Double Ratchet, because a receiver who keeps old inbound chain state can still decrypt delayed or replayed older indices (implementations typically window this and reject duplicates).
- **Post-compromise security (weak):** theft of a member’s current inbound sender-key state lets the attacker decrypt *future* messages from that sender until the sender rotates and distributes a new SKDM. PCS is restored only by rotation (membership change, periodic rotation, or an explicit “reset group encryption”). This is the standard sender-keys / Megolm caveat and must be described honestly. It is still a large improvement on static `nacl.box`, where compromise of the identity key decrypts the entire history.
- **Removed members:** they already know every sender key they were given. Future confidentiality against them *requires* every remaining sender to rotate. See §8.
- **New members:** they receive current SKDMs and can read messages after that point, not history. That is intended.

### 5.4 Multi-device

This migration stays **single device** (device id `1`). libsignal can represent multiple devices (`ProtocolAddress(name, deviceId)`), and recent libsignal releases replaced Sesame session management with Tahini, but linking a second device, transferring history, or sharing an identity private key across phones is a separate project.

Honest claim after the migration: “Encryption keys live on this phone. A new phone creates a new identity; people you chat with will be asked to verify you again. Earlier messages stay on the old phone.”

Do not claim multi-device, encrypted iCloud backup, or “your chats follow you to a new iPhone” until that work exists.

### 5.5 What does not change

- Announcements remain readable on the server.
- Metadata remains visible to the server.
- Abuse reports still work by decrypting chosen messages on the reporter’s phone and uploading plaintext evidence they selected.
- WebRTC media is already DTLS-SRTP; the gain on calls is authenticating signalling under the ratchet so the server cannot swap DTLS fingerprints.

## 6. Licensing go/no-go (must be decided before any native module is added)

`signalapp/libsignal` is licensed **GNU AGPL-3.0** (the repository states AGPLv3; downstream analyses of current file headers also treat it as AGPL-3.0-only). Signal’s README says the repository is for Signal’s own clients and servers and that use outside Signal is unsupported.

Implications for a closed Understage iOS app:

1. **Linking libsignal into the app creates a combined work.** Distributing that app requires licensing the combined work under AGPL-3.0 and offering complete corresponding source to recipients.
2. **AGPL §13** (network use) can also require offering source to users who interact with a networked service built on the combined work. How far that extends to a mobile client plus a separately written backend is a question for counsel, not for this note. The conservative reading is: if the client is AGPL because it links libsignal, treat the shipped application as AGPL.
3. **Apple App Store distribution is a separate problem even for an AGPL-compliant app.** Apple’s terms add restrictions that AGPL §6 does not allow a licensee to impose. The old C library `libsignal-protocol-c` carried an explicit “Additional Permissions For Submission to Apple App Store” (Signal’s 2016 license-update post). The current Rust `libsignal` **does not** carry that §7 additional permission. Issues requesting it (`signalapp/libsignal#684`, `#677`) were still open and only “acknowledged” as of August 2026. No public Signal commercial license is advertised.
4. Dynamic linking does not avoid the combined-work analysis.
5. Understage’s tree currently contains an MIT license text inherited from Expo tooling. Shipping libsignal would not be a quiet dependency bump; it is a product-licensing event.

**Go criteria (all required) before implementation:**

- Written decision that Understage will be distributed under AGPL-3.0 **and** that App Store conveyance is covered either by a Signal-granted additional permission or by advice from counsel the owner accepts; **or**
- A written commercial license from Signal Messenger, LLC covering this product (not known to be offered publicly); **or**
- A written decision to abandon official libsignal and implement the fallback in §4 (vodozemac or OpenMLS).

Until one of those exists, the correct engineering stance is the one already in the product: keep the 50-member encrypted-group cap, and do not claim 200-person E2EE group chat.

This document does not purchase or request a license.

## 7. Key distribution and server shape

Sender keys are useless without pairwise sessions to carry the SKDM. The server becomes a prekey directory and an opaque ciphertext relay. It still never sees plaintext or private keys.

### 7.1 Device identity

Each phone holds, in native code:

- A libsignal `IdentityKeyPair` (X25519). The existing TweetNaCl identity is *not* a drop-in libsignal identity for new sessions; treat it as a legacy key kept only to decrypt old `nacl.box` history (see §10).
- A numeric `registrationId`.
- A `deviceId` of `1` (single device).
- Signed prekey (rotated on a schedule, for example every 7–14 days).
- A batch of one-time X25519 prekeys (for example 100).
- A batch of Kyber/ML-KEM prekeys for PQXDH, including one last-resort prekey that is not deleted on use.

Private material never leaves the device. Public material is uploaded to Understage’s server.

### 7.2 New tables (conceptual)

- `device_keys(user_id, device_id, registration_id, identity_key, signed_prekey_id, signed_prekey, signed_prekey_sig, kyber_last_resort_id, kyber_last_resort, kyber_last_resort_sig, uploaded_at)`
- `one_time_prekeys(user_id, device_id, key_id, public_key, created_at)` — row deleted inside the same transaction that returns it.
- `kyber_prekeys(user_id, device_id, key_id, public_key, signature, last_resort, created_at)` — one-time Kyber prekeys are marked used or deleted atomically; the last-resort key is reused when the one-time pool is empty (this weakens PQ forward secrecy for that session and must be rare).
- `messages.envelope_version` — `1` = legacy `nacl.box` payloads; `2` = Signal/sender-key envelope.
- For version 2 group messages, store **one** ciphertext (a single `message_payloads` row, or a `messages.ciphertext` column), not one row per member. Receipts stay per recipient.

Existing `users.identity_key` remains during the dual-stack period so old clients and historical decrypt still resolve a public key.

### 7.3 New endpoints (conceptual)

- `PUT /me/keys` — extend, do not break, the current `{ identityKey }` body. Version 2 uploads `{ protocol: "signal", deviceId, registrationId, identityKey, signedPreKey, oneTimePreKeys[], kyberPreKeys[] }`.
- `POST /me/keys/prekeys` — replenish one-time and Kyber prekeys when the client’s low watermark fires (for example fewer than 50 remaining).
- `GET /me/keys/status` — remaining one-time / Kyber counts for this device (no private material).
- `GET /users/:id/prekey-bundle` — returns that user’s device bundle and **consumes** one one-time prekey and one one-time Kyber prekey atomically. If the one-time pool is empty, return the signed prekey (and last-resort Kyber) only; the client must treat that as weaker forward secrecy, log it, and the owner of the bundle must replenish.
- Existing `GET /users/:id` may keep returning the published identity public key for safety numbers and for legacy decrypt.

Rate-limit bundle fetches. Never hand the same one-time prekey to two callers.

### 7.4 Establishing a 1:1 session

1. Alice fetches Bob’s prekey bundle.
2. Native `processPreKeyBundle` creates a Double Ratchet session, stored in `SessionStore`.
3. Alice’s first message is a `PreKeySignalMessage`; Bob’s `signalDecryptPreKey` consumes the matching local one-time prekeys and persists the session.
4. Later messages are ordinary `SignalMessage` (Whisper) on the ratchet.

These pairwise sessions are also the only channel used to send SKDMs.

### 7.5 Stores on the phone

Libsignal requires application-provided stores: `IdentityKeyStore`, `PreKeyStore`, `SignedPreKeyStore`, `KyberPreKeyStore`, `SessionStore`, `SenderKeyStore`. Records are opaque binary pickles.

Recommended layout:

- Identity private key and a database wrapping key: iOS Keychain, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` (same accessibility as today).
- Everything else (prekeys, sessions, sender keys): an on-device SQLite file encrypted at rest (SQLCipher or equivalent), opened with the Keychain wrapping key.

Do not keep libsignal pickles in AsyncStorage or in the existing unencrypted app cache database. Do not back the file up to iCloud.

JavaScript should never see raw private keys. The Expo module exposes `encryptDirect`, `decryptDirect`, `createSkdm`, `processSkdm`, `groupEncrypt`, `groupDecrypt`, `safetyNumber`, and `exportPublicBundle` over opaque handles or the conversation/user ids.

## 8. Group membership changes and cost at 200

### 8.1 First send in a group

Before Alice sends her first sender-key message in a group:

1. She creates (or reuses) a pairwise session with every other member who does not yet have one, using §7.4. Worst case at 200: 199 bundle fetches and 199 session setups. Sessions persist, so this is once per pair, not once per message.
2. She creates a sender-key record for `(conversationId, Alice, newDistributionId)` and an SKDM.
3. She encrypts that SKDM to each other member on the pairwise session (199 small messages). These can be dedicated control envelopes, not visible as chat bubbles.
4. She `groupEncrypt`s the plaintext to produce one `SenderKeyMessage`.
5. The server stores and fans out that single ciphertext.

After step 3, Alice’s later messages skip 2–3 until she rotates.

### 8.2 Member added

The new member must not read history. Each existing sender, on their next send (or immediately, if already in the group and active), transmits their *current* SKDM to the new member over a pairwise session. Cost: O(1) pairwise message per active sender. No rotation is required merely because someone joined.

### 8.3 Member removed or leaves (must rotate)

The removed member still has every SKDM they processed. **Eager rotation is required** so they cannot read subsequent messages:

- Every remaining member who has a sender-key record generates a new `distributionId` and new sender key, then distributes a fresh SKDM to each of the other `n - 1` remaining members.
- Eager, all-at-once cost at `n = 200`: `200 × 199 = 39,800` pairwise SKDMs.
- Each SKDM is small (a few hundred bytes of plaintext; under 1 KB after ratchet encryption). A full eager rekey is on the order of 15–40 MB of ciphertext and a burst of 1:1 deliveries — expensive as a one-off, cheap compared with 200 `nacl.box` operations *per chat message* forever.
- **Do not use unbounded lazy rotation on remove.** A sender who “will rotate on next send” leaves a window where the removed member can still decrypt that sender’s traffic. Lazy rotation is acceptable for *periodic PCS* (see §8.4), not for eviction.

Implementation notes:

- Run the rekey in the background with parallelism and backoff.
- Surface a non-blocking status such as “Updating group encryption…” rather than freezing the composer for minutes.
- If a pairwise session or SKDM delivery fails, retry from the outbox; do not send a new group ciphertext under an old `distributionId` once that member has been removed.
- The server should keep enforcing membership on delivery (a removed user must not receive new ciphertexts) — that is access control, not cryptography. Cryptographic eviction is the rotation.

### 8.4 Periodic rotation

To restore some group PCS after a silent compromise, rotate each sender key on a schedule (for example every 7 days or every several hundred messages from that sender). Cost per rotation per sender: `n - 1` SKDMs (~200 messages, a few hundred KB). This can be lazy and staggered.

### 8.5 Why not “just raise the fan-out cap to 200”

That would make the video’s headcount true and leave every other cryptographic claim false: still no forward secrecy, still no prekeys, still 200 boxes and 200 database rows per message. It is not this migration.

## 9. Attachments and call signalling

### 9.1 Attachments and voice notes

Keep the current two-layer design:

1. Encrypt the file (and voice-note bytes) with a fresh content key. During dual-stack this may remain `nacl.secretbox`; after cutover prefer AES-256-GCM (or libsignal’s AES-256-GCM-SIV) with a random key and nonce.
2. Put `{ attachmentId, key, nonce, mime, name, size, … }` inside the *message* plaintext.
3. Encrypt that plaintext with the Double Ratchet (1:1) or sender keys (group).
4. Upload only the opaque file ciphertext to `POST /attachments`.

No file key is sent in a per-recipient fan-out anymore. A 200-person voice note is one encrypted blob plus one sender-key message, not one blob plus 200 boxes of the file key.

Existing v1 attachments remain decryptable as long as the legacy identity secret is kept and the `AttachmentRef` inside the old `nacl.box` plaintext can still be opened.

The 25 MB client limit can stay. This section does not change upload UX.

### 9.2 Calls

Media path is unchanged: `react-native-webrtc`, DTLS-SRTP, STUN today, TURN still an external blocker.

Signalling (SDP offers/answers and ICE candidates) must move from `nacl.box(identity)` to `signalEncrypt` on the caller/callee pairwise session. That gives forward secrecy on SDP and stops a stolen long-term identity key from opening recorded signalling, and it keeps the server from substituting DTLS fingerprints if the pairwise session is authentic.

Group calls are not in the video and stay out of scope. There is no sender-key media path to design here.

CallKit, PushKit, and a TURN server remain independent production blockers. This migration does not make “encrypted calls between two accounts” tested; it only changes how signalling is sealed once calling is tested.

## 10. Data migration

There is no cryptographic upgrade path that turns a historical `nacl.box` ciphertext into a `SenderKeyMessage`. The identity keys, nonces, and algorithms differ. Plan for coexistence, then a cutover.

### 10.1 What stays readable locally

Plaintext already sitting in the device’s message cache (SQLite via `cache.upsertMessage`) remains readable after the upgrade. Those rows store `body: PlainMessage`. The migration must not wipe the local message database.

Legacy identity secret keys in the Keychain (`identity_${userId}`) must be **kept** after the libsignal identity is created, under a distinct key (for example `legacy_identity_${userId}`), so that:

- v1 ciphertexts still on the server can be decrypted on sync;
- the user can open old chats after an app update on the same phone.

If the legacy secret is deleted, server-held v1 history for that user becomes unreadable on that phone. There is no recovery.

### 10.2 What is dropped

- Test and seed conversations (Hamlet demo crew, smoke users, synthetic messages created by `server/scripts/*`) should be **reset**, not converted. They were built with `encryptForRecipients` and have no production value.
- Any attempt to re-encrypt server history into sender keys would require every historical sender to be online with their old secret and would still not provide forward secrecy for that history. Do not do this.
- A brand-new phone, as today, cannot read old ciphertext. Keep saying so.

### 10.3 Dual-stack transition

Introduce an envelope version on `POST /conversations/:id/messages`:

- **v1:** current `{ payloads: [{ recipientId, nonce, ciphertext }] }`. Server continues to require one payload per member. Clients that still have the legacy identity decrypt with `decryptPayload`.
- **v2:** `{ envelopeVersion: 2, protocol: "signal", msgType: "prekey" | "whisper" | "senderkey", distributionId?: string, ciphertext: string, deviceId?: number }`. For `senderkey`, the server stores one ciphertext and delivers the same bytes to every current member. For 1:1, one ciphertext to the peer; the sender already has plaintext locally.

Rules:

- A conversation becomes “v2-capable” when every member has uploaded a Signal bundle (`device_keys` row). Until then, senders keep using v1, and the 50-member cap still applies to that conversation.
- Once every member is v2-capable, new messages from updated clients are v2. Old v1 rows remain in `message_payloads` and are decrypted with the legacy key.
- The server rejects a v2 `senderkey` send if any current member lacks a bundle, or if a listed recipient is no longer a member.
- Clients must not try to run v2 ciphertext through `nacl.box.open`, or v1 through `groupDecrypt`.

### 10.4 Test data

Development databases used for the 200-person exercise must be created *after* v2 exists. Do not insert 200 synthetic members into a production-like account’s workspace, and do not expect existing Hamlet messages to decrypt under sender keys.

Recommended reset for local/dev:

1. Stop sending v1 in dev once v2 ships to the Simulator build.
2. Recreate a dedicated development workspace (not the owner’s personal chats) with synthetic users who each have a Signal bundle.
3. Leave leftover v1 rows in old databases to exercise historical decrypt; do not treat them as sender-key coverage.

### 10.5 Safety numbers during transition

A user will briefly have two public identities (legacy X25519 and libsignal identity). Safety-number screens must show the libsignal fingerprint once both peers are on v2, and must not silently mix the two. Contacts verified against the old number need to verify again. That is expected and should be explained once, not hidden.

## 11. Native build impact

This Mac is Intel (`x86_64`) running macOS 15.7.7, Xcode 26.3, Swift 6.2, iOS Simulator runtime 26.3. The successful Understage binary was built with `EXPO_USE_PRECOMPILED_MODULES=0` so every Expo module compiles from source, plus a `patch-package` Swift 6.2 fix for `expo-modules-jsi`. There is no EAS and no cloud build.

### 11.1 Why a native module is required

Hermes cannot load `@signalapp/libsignal-client`. There is no supported pure-JS official implementation. The app therefore needs a local Expo module, for example `modules/understage-signal`, whose iOS side links official `LibSignalClient` (UniFFI-generated Swift over the Rust static library).

That **requires a native rebuild**. It cannot be hot-patched onto the existing `Understage.app` with Metro alone. It should not require discarding Xcode, downgrading Expo SDK 58 or React Native 0.88.1, or removing the existing Swift 6.2 patch.

### 11.2 Toolchain

- Rust via `rustup`, with targets `x86_64-apple-ios` (Intel Simulator) and `aarch64-apple-ios` (physical iPhone).
- An Apple Silicon Simulator slice (`aarch64-apple-ios-sim`) is not needed for this Mac and should not replace the x86_64 Simulator slice.
- UniFFI / the libsignal Swift package build, Xcode 26.3, and the iOS 26.2/26.3 SDK already used for the current app.
- No prebuilt Node add-ons. Prefer building an XCFramework locally so the same artifacts link into Debug-iphonesimulator and, later, Debug-iphoneos.

### 11.3 Risks specific to this machine

- libsignal’s Rust build is heavy; expect a long first compile on Intel.
- UniFFI-generated Swift may need Swift 6 concurrency / Sendability fixes under Swift 6.2, similar in kind (not in patch) to the existing `expo-modules-jsi` patch. Those fixes belong in our wrapper or a documented local patch, not by editing Xcode.
- `EXPO_USE_PRECOMPILED_MODULES=0` must stay set; a precompiled libsignal binary that lacks `x86_64-apple-ios` will fail on this Simulator.
- Linking another Rust static library can surface duplicate symbols (allocator, panic handler) against other native deps. That is a spike item, not an afterthought.
- The wrapper must compile for the Simulator first (the environment already proven) and only then for `arm64` device.

### 11.4 What not to do

- Do not consume EAS build minutes or paid cloud compile services.
- Do not drop Expo modules that already compile.
- Do not replace TweetNaCl in server tests until a Node-side test double exists (the official Node package *can* be used in `server/test` on macOS, which is useful for protocol fixtures).
- Do not claim the existing Simulator build “already includes” libsignal.

Android Java bindings are a later phase. This document’s first native target is iOS.

## 12. Test plan

A feature is complete only if the behaviour has been tested. Protocol work that only compiles is not done.

### 12.1 Native spike (Phase 1)

- Build `LibSignalClient` for `x86_64-apple-ios` on this Mac with Xcode 26.3 / Swift 6.2.
- Link it into a scratch Expo module in the existing app target without removing current features.
- Round-trip `IdentityKeyPair` generate → pickle → restore from Keychain-backed storage.
- Confirm the existing Understage target still launches in the iPhone 17 Pro Simulator after the module is linked (launch test, not a full product regression).

### 12.2 Host-side protocol tests

Use `@signalapp/libsignal-client` on Node (macOS) as an independent implementation:

- Two virtual devices: PQXDH session, plaintext recovered, out-of-order delivery, duplicate rejection.
- Three virtual devices: SKDM distribution, `groupEncrypt` / `groupDecrypt`, duplicate `SenderKeyMessage` rejected.
- After a simulated member remove, an old SKDM holder must fail to decrypt a post-rotation `SenderKeyMessage`.
- Prekey bundle consumption is atomic (a second fetch does not return the same one-time prekey).

These tests prove the *protocol choice*. They do not prove the React Native module.

### 12.3 Server tests (vitest)

- `PUT /me/keys` v2 validation; old `{ identityKey }` still accepted during dual-stack.
- `GET /users/:id/prekey-bundle` deletes the issued one-time prekey in the same transaction; concurrent fetches cannot share it.
- Empty one-time pool returns signed prekey + last-resort Kyber and is visible in metrics/logs.
- `POST /conversations/:id/messages` accepts v1 and v2; v2 `senderkey` stores one ciphertext; removed members are not listed as recipients.
- Existing 16 backend tests continue to pass; add parallel fixtures rather than breaking current `encryptForRecipients` tests until cutover.

### 12.4 Application tests in the Simulator

- Two Simulator-backed accounts (or one Simulator and one automated client using the Node bindings against the local server): 1:1 send, receive, delivery/read, history after relaunch.
- Three accounts in one group: text, then a voice note, then an image; all three decrypt; chat preview shows plaintext after open/sync (no stuck “Encrypted message” after a v2 decrypt).
- Add a fourth member: they cannot read earlier messages; they can read new ones.
- Remove a member, wait for rekey to finish, confirm the removed account cannot decrypt a new group message, and remaining members can.
- Legacy v1 messages planted before the upgrade still open on a phone that kept the legacy identity.
- Safety number matches on both sides for a v2 pair; it changes when an identity is replaced.
- Call signalling: if a 1:1 call can be placed in-Simulator, confirm SDP is not sent as a v1 `nacl.box` envelope after the signalling switch. If a two-endpoint call cannot be executed, record calling as untested — do not mark it complete.

### 12.5 200-person development workspace

After 12.4 passes, create an **isolated** development workspace (not production accounts) with about 200 synthetic members, several departments, mixed time zones, and a workspace conversation:

- One sender posts a text message; server stores one v2 ciphertext; a sample of recipients (not necessarily all 200 interactive UI sessions) decrypt successfully via automated clients.
- Measure send time, ciphertext size, and memory on the sending Simulator.
- Remove one member and measure eager rekey time and traffic; confirm that member’s client cannot decrypt the next message.
- State the tested maximum, not “200 works” based on a unit test with three participants.
- If automated clients cannot decrypt, the feature is not complete, even if the sender’s UI looks fine.

### 12.6 Physical iPhone

Camera QR, microphone voice notes, background behaviour, Keychain-on-device, and calling between a phone and the Simulator are **untested until they run on a device**. This document does not treat them as passed.

### 12.7 Security regressions that fail the migration

- Logging private keys, pickles, SKDMs in plaintext, or prekey private material.
- Uploading the sender key or identity secret to the server “for backup”.
- Accepting a replaced identity key without surfacing a safety-number change.
- Sending a group message under a pre-removal `distributionId` after a member was removed.
- Claiming Secure Enclave, multi-device, or “Signal-grade group PCS” in UI copy.

### 13.1 Risks

| Risk | Impact | Mitigation |
|---|---|---|
| AGPL + missing App Store extra permission | Cannot ship a closed App Store build that links libsignal | Phase 0 written decision; otherwise use the §4 fallback |

| Claiming video parity early | False production readiness | §14 copy table; tests in §12 gate each claim |

## 15. Open decisions

1. **Licensing (blocking).** AGPL + App Store additional permission, a Signal commercial license, or a fallback library (vodozemac or OpenMLS). No native module until this is written down.
2. **Fallback if Phase 1 cannot build libsignal on this Intel / Xcode 26.3 Mac.** Revisit vodozemac or OpenMLS rather than lowering cryptographic ambition back to “raise fan-out to 200”.
3. **Periodic sender-key rotation interval.** Suggested starting point: 7 days or 500 messages from that sender, whichever first.
4. **Whether to implement an SE-backed wrapping key** so privacy copy can say “wrapped with a Secure Enclave key”. This is optional and is not required for protocol correctness.
5. **Physical iPhone testing** remains blocked on a cable/adapter, trusting the device, and an Apple ID in Xcode → Settings → Accounts.
